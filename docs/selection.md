# 저장소 선정 과정

## 선정 기준

- 단순 문서 번역이 아닌 **코드 기여**일 것
- 팀원이 이해하고 고칠 수 있는 난이도의 이슈가 여러 개 있을 것
- 외부 기여자의 PR을 실제로 받아 주는 저장소일 것
- 프로젝트별 **기여 정책**(CONTRIBUTING, AGENTS.md 등)을 확인할 것 (5주차 수업 내용)

## 후보 비교

> 수치는 2026-10-11에 GitHub API로 조회한 값입니다.

| 항목 | xyflow | Nushell | **Mermaid** |
|---|---|---|---|
| GitHub Stars | 약 3.9만 | 약 4.1만 | **약 9.1만** |
| 기여 정책 | 제약 없음 | **AGENTS.md 규칙상 제외** | 제약 없음 |
| 작업해도 되는 이슈 표시 | 따로 없음 | 따로 없음 | **`Status: Approved` 라벨** |
| 버그 재현 방법 | 브라우저에서 직접 조작 | Rust 빌드 필요 | **텍스트 입력 → 그림으로 바로 확인** |
| 결과 | 보류 | 제외 | **선정** |

## Mermaid를 고른 이유

1. **영향 범위가 넓습니다.** 주간 npm 다운로드가 약 1,800만 회이고, GitHub과 Notion 마크다운에 기본으로 들어가 있습니다.
2. **들어가기 쉬운 구조입니다.** 메인테이너가 작업해도 되는 이슈에 `Status: Approved` 라벨을 붙여 둬서 따로 허락을 받을 필요가 없습니다. 문법 버그는 "입력한 텍스트 → 잘못 그려진 그림"으로 재현과 테스트가 명확합니다.
3. **수업 기준을 만족합니다.** 저장소의 기여 가이드, PR 템플릿, 워크플로를 확인했고 우리 방식의 기여를 막는 규칙이 없었습니다.

참고로 외부 PR이 머지되기까지 걸리는 시간은 Mermaid가 세 후보 중 가장 길었습니다(중간값 약 5일). 그래서 "빨리 머지돼서"가 아니라 위 세 가지 이유로 골랐습니다.

## 이슈 선정

`Status: Approved` 이슈 중에서 다음 조건으로 골랐습니다.

- 최신 develop 코드에서 직접 재현될 것
- 다른 사람이 이미 작업 의사를 밝혔거나 PR을 올리지 않았을 것
- 팀원마다 렌더링 흐름의 다른 단계를 맡도록 나눌 것

재현해 보니 이미 고쳐져 있거나 다른 사람이 가져간 이슈(#7042, #7033, #7026 등)는 후보에서 뺐습니다.
